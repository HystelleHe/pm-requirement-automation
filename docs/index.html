一直在想怎么把重复的工作变得更可持续。

三个想法

构建 Workflow 时反复回想的事

不是方法论，就是做了一段时间之后，觉得这三件事想清楚了会省很多麻烦。

第一件事
本地化
工具跑在自己机器上，
数据不离开本地

用 SaaS 工具很方便，但有一种隐患：哪天涨价了、服务关了，或者网断了，workflow 就停了。更烦的是，历史数据可能也跟着没了。

所以现在倾向于把能自建的都 Docker 跑在本地——n8n、Langfuse、Qdrant 都是这样。API Key 放在 .env 文件里，不经过任何第三方平台。调研报告、PRD 草稿也都落在本地磁盘，不只活在某个 SaaS 的数据库里。

这样至少有一个感觉：东西是自己的，不是租来的。

第二件事
资产化
把可复用的部分
显式管理起来

以前写 Prompt 都是散在聊天窗口里，效果好的那条根本找不回来。改了一版又不知道哪版更好，完全没有积累感。

后来把 Prompt 全部改成 .md 文件放在项目仓库里，git 版本管理，改了就 commit。跑出来的调研报告、PRD 也都落到 outputs/ 目录，不扔掉。好的案例再加到 Eval 数据集里。

慢慢地，每次运行都在给下一次变好提供素材——有点像在攒利息，而不是每次都从零开始。

第三件事
可迁移
整套东西换个环境
还能跑起来

换电脑的时候，或者某个工具出问题的时候，最怕的就是「这套东西只能在那台机器 / 那个平台上跑」。

所以把业务逻辑全部写在独立的 FastAPI 服务里，n8n 只负责触发和 HTTP 调用——这样今天换成 cron、明天换成 Slack Bot，逻辑不用重写。模型配置全走环境变量，换个 LLM 供应商改一行 .env 就行。每个功能也有 CLI 命令兜底，不依赖任何编排工具也能跑。

迁移单元是一份 docker-compose.yml 加一份 .env，拷过去就能起。

跑通之后发现的一件事

开放型需求（比如「我们要不要做 X」）被硬套进 PRD 模板会很奇怪——PRD 假设你已经决定做了，但这类需求根本还没到那一步。所以加了 Discover 路径，只输出洞察备忘录，不强行生成 PRD。

Discover 路径

Critic 为什么用不同家的模型

PRD 生成用 Kimi，审校用 GLM（不同厂商）。同一个模型既写又改，容易对自己的表达方式有盲点，改的时候放水。跨家之后，GLM 确实能发现一些 Kimi 没注意到的结构问题。

跨家审校

Skill Library 是最早积累下来的东西

五个核心 Prompt（research / breakdown / prd_writer / prd_critic / insight_memo）都以 .md 文件存在仓库里，启动时自动同步到 Notion。哪天想换 workflow，这些 Prompt 直接复用。

资产化

n8n 只做"穿针引线"

n8n workflow 里只有 5 个 HTTP 节点，所有判断逻辑都在 FastAPI 服务里。好处是 n8n 如果哪天不想用了，换成 cron 或者其他触发方式，一行业务代码都不用动。

其实这套东西不只适合 PM

只要是高频、结构相对固定的工作，大概都能套。下面几个只是随手想的。

📬

周报 / 月报

从多个数据源聚合 → LLM 写初稿 → 定时推送。Prompt 版本化之后，改风格只改一个文件。

🧑‍💻

代码 Review 辅助

PR 触发 → LLM 审查打标 → 评论写回 GitHub。跨家 Critic 同样适用，不同模型发现不同类型的问题。

📰

行业情报聚合

定时抓 RSS + 网页 → 摘要 → 落库。每篇摘要都是资产，时间长了可以回头找趋势。

🗂️

会议纪要结构化

录音转文字 → 提取决策 / Action Item → 推 Notion。产出可回溯，慢慢变成团队知识库。

🎯

培训素材生成

输入知识点 → 自动出题 + 答案 + 难度分级。出题 Prompt 沉淀到 Skill Library，下次复用。
