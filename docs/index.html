个人生产力 · Workflow 方法论

个人 Workflow 通用思路

用三个原则构建任何自动化工作流：
把重复工作变成可持续运行、可积累、可迁移的个人资产

⬡ 本地化 ◈ 资产化 ⟳ 可迁移
核心理念

三个原则，适用于所有 Workflow

这三条不是技术要求，而是在「做了再说」过程中反复被验证的判断标准。构建任何新 workflow 之前，先把这三条想清楚。

原则 01
本地化
工具跑在自己的机器上
数据不离开本地
是什么

核心工具（编排、观测、向量库）用 Docker 自建，运行在本机；API Key 在本地 .env 文件里，不上传任何 SaaS 平台。

为什么重要
  • SaaS 订阅有不确定性：涨价、关闭、断网都不影响你的工作流继续运行
  • 数据主权在自己手里——调研报告、PRD 草稿、历史产出都落在本地磁盘
  • 调试更方便：直接看 docker logs，不需要在云端 dashboard 里找原因
  • 成本可控：只付 LLM API 调用费，不付平台托管费
怎么做
  • n8n / Langfuse / Qdrant 全部 Docker 自建，一条 docker compose up -d 启动
  • 所有凭据集中在 .env，加入 .gitignore，永远不入 git
  • 产出目录（outputs/）也在本地，git 只管代码不管数据
原则 02
资产化
把重复工作中可复用的部分
显式管理起来
是什么

Prompt 不散在聊天框里，而是以文件的形式版本化管理；每次运行的产出落盘，可积累成 Eval 数据集；Skill Library 是跨 workflow 复用的提示词仓库。

为什么重要
  • Prompt 不版本化，改了就不知道哪版效果好，无法系统性迭代
  • 每次手写调研报告 / PRD 都是沉没成本；跑出来的文档是「会增值的资产」
  • 历史产出 + 人工评分 = 未来 Eval 数据集的原料，是质量护城河
  • Skill Library 建好后，新 workflow 复用已有 Prompt 而不是从零写
怎么做
  • Prompt 以 .md 文件存在项目仓库里（skill-library/），git 版本管理
  • 同一份 Prompt 同步到 Notion Skill Library 作为「可共享资产」
  • 每次运行的产出自动落到 outputs/{req_id}/ 目录
  • 建 Eval 数据库，把觉得「这条产出不错」的加入金标集
原则 03
可迁移
整套系统可以在任何环境
一键重建
是什么

docker-compose.yml 是迁移单元，.env 是唯一需要填的配置；能力层（业务逻辑）和编排层（触发机制）分离，可以独立替换任何一侧。

为什么重要
  • 换电脑、换服务器，不应该丢失工作——一份 compose 文件解决
  • 今天用 n8n 触发，明天改成 cron/Slack Bot/GitHub Actions，业务逻辑不需要动
  • 不被任何模型绑定——环境变量换个 LLM_MODEL 就能切换模型供应商
  • CLI 兜底：即使编排层全挂了，手动跑一条命令也能产出结果
怎么做
  • 能力层写成独立 FastAPI 服务，有 CLI 入口，不依赖编排层
  • 编排层（n8n）只做触发 + HTTP 调用，不含任何业务逻辑
  • 模型配置全通过环境变量注入，代码里不写死任何模型名
  • docker-compose.yml + .env.example + README = 完整交付物
通用框架

基于这三条，怎么构建任何 Workflow

从识别重复工作，到可持续运行的自动化系统，一共五步

1

识别「值得自动化」的重复工作

不是所有重复工作都值得自动化。判断标准：频率 × 单次耗时 × 质量可标准化程度。竞品调研 + PRD 是高频、高耗时、且结构相对固定的任务，是好的切入点。反例：每次都高度个性化的战略决策，不适合自动化。

理念：资产化的起点是认清「哪些工作在重复」
2

把「工作步骤」拆成独立能力

手动工作时你怎么做的，流程图画出来。每个「步骤」对应一个 Agent 或函数，输入/输出接口定义清楚。拆得越细，后续替换单个环节越容易。竞品调研 → 需求拆解 → PRD 撰写是三个独立能力，每个可以单独跑、单独测、单独迭代。

理念：能力层独立 = 可迁移的基础
3

把 Prompt 写成文件，加版本管理

每个能力对应一个 skill .md 文件，包含 System Prompt + User Prompt 模板 + 输入变量声明。改 Prompt 就改文件，git commit 留记录，回滚靠 git checkout。不要把 Prompt 散在代码字符串里——改了就找不到上一版了。

理念：资产化 = Prompt 版本化
4

用薄编排层串联，别把业务逻辑放进去

n8n / cron / GitHub Actions 只负责：定时触发 → 调 HTTP 接口 → 传结果。业务判断（该走哪条路径？这次需不需要 Critic？）全在能力层决定。编排层越薄，替换成本越低；能力层越独立，测试越方便。

理念：可迁移 = 编排层和能力层解耦
5

Docker 化，落盘产出，补 CLI 兜底

docker-compose.yml 把所有服务打包，.env.example 是给未来的自己写的说明书。产出自动存到本地目录。每个核心功能补一个 CLI 命令——这不是「备用」，而是「最快的调试方式」和「编排层挂了时的救命绳」。

理念：本地化 + 可迁移 的落地形式

本地化 的体现

n8n / Langfuse / Qdrant 全 Docker 自建；.env 在本机，Notion API Key 不经过任何第三方平台；调研报告、PRD 全部落到本地 outputs/ 目录。

⬡ 本地化

资产化 的体现

5 个 Skill（research / breakdown / prd_writer / prd_critic / insight_memo）以 .md 文件存在 skill-library/，启动时同步到 Notion Skill Library；历史 PRD 产出积累成 Eval 数据集原料。

◈ 资产化

可迁移 的体现

FastAPI 能力层独立于 n8n，可用 cron / Slack / GitHub Actions 替换编排；LLM_MODEL_* 环境变量随时换模型；pm-workflow CLI 在 n8n 宕机时也能手动触发全流程。

⟳ 可迁移

关键设计决策：跨家 Critic

PRD 生成用 Kimi-K2（Moonshot），审校用 GLM-5（智谱）。同模型既当作者又当评审容易漏掉明显矛盾——跨家可以暴露不同模型的「盲点差」。这也是资产化的一部分：审校逻辑可复用到其他文档生成 workflow。
